# BizFlow Business Setup Guide

This guide explains how a platform administrator creates a business, assigns its application, provisions an isolated database, and gives the business owner access.

## 1. Choose an isolated database backend

For local development or a small single-server deployment, SQLite creates one file
per business and does not require PostgreSQL:

```bash
unset BIZFLOW_DB_ENGINE
export BIZFLOW_BUSINESS_DATABASE_DIR="$PWD/business_databases"
```

Create the directory and keep it outside version control:

```bash
mkdir -p "$BIZFLOW_BUSINESS_DATABASE_DIR"
```

For production, PostgreSQL is recommended. Continue with the PostgreSQL setup below.

For production, use a managed PostgreSQL instance or a secured PostgreSQL server.

For local development with Docker:

```bash
docker run --name bizflow-postgres \
  -e POSTGRES_DB=bizflow_core \
  -e POSTGRES_USER=bizflow \
  -e POSTGRES_PASSWORD='replace-this-local-password' \
  -p 5432:5432 \
  -d postgres:16-alpine
```

Wait until PostgreSQL is ready:

```bash
docker exec bizflow-postgres pg_isready -U bizflow -d bizflow_core
```

The PostgreSQL role must be able to create databases:

```sql
ALTER ROLE bizflow CREATEDB;
```

Use a stronger, separately managed secret outside source control.

## 2. Configure BizFlow

From the `bizflow/` directory:

```bash
export BIZFLOW_DB_ENGINE=postgresql
export BIZFLOW_DB_NAME=bizflow_core
export BIZFLOW_DB_USER=bizflow
export BIZFLOW_DB_PASSWORD='replace-this-local-password'
export BIZFLOW_DB_HOST=127.0.0.1
export BIZFLOW_DB_PORT=5432
```

Run the central migrations:

```bash
../.venv/bin/python manage.py migrate
../.venv/bin/python manage.py createsuperuser
```

Start Django:

```bash
../.venv/bin/python manage.py runserver
```

## 3. Create a business

1. Sign in at `/login/` using a staff account.
2. Open `/platform/`.
3. Select **Create business**.
4. Enter:
   - Business name.
   - Unique URL slug.
   - Initial status, normally `Pending`.
   - Application type.
5. Save the business.

The application selection determines which application migrations are installed in the isolated database.

## 4. Provision the isolated database

From the platform business list, select **Provision**.

The provisioning service performs these steps:

### Step 1: Create database identity

The platform creates a database name based on the immutable business UUID:

```text
bizflow_business_<business_uuid_without_dashes>
```

The database name is generated by the platform and is not supplied by the browser.

### Step 2: Create PostgreSQL database

The platform PostgreSQL connection creates the business database. The business database uses the same configured host, port, user, and password connection settings, but has a separate database name.

### Step 3: Apply application migrations

Only the selected application is migrated:

- `salonNEXT` migrations for a SalonNEXT business.
- `pharmacyB` migrations for a PharmacyB business.
- `graceryshopA` migrations for a GraceryShopA business.

### Step 4: Create the business owner membership

The business creator becomes the initial business owner. This membership is stored centrally and is used by the business access middleware.

### Step 5: Activate the business

The business becomes `Active` only after database creation, migrations, and owner membership succeed.

## 5. Verify provisioning

Check the business list and confirm:

- Business status: `Active`.
- Database status: `Ready`.
- Provisioning attempt: `Succeeded`.
- All provisioning steps: `Succeeded`.

You can also inspect the Django admin:

```text
/admin/
```

Relevant records:

- Business.
- Business database.
- Provisioning attempt.
- Provisioning step.
- Business application.
- Business membership.

## 6. Test business login

1. Visit `/login/`.
2. Sign in as the business owner.
3. If the user belongs to one active business, BizFlow redirects directly to its dashboard.
4. If the user belongs to several businesses, BizFlow displays the business selector.

The user cannot gain access by changing the business slug in the URL. Membership and business status are checked on every business request.

## 7. Test SalonNEXT

For a SalonNEXT business:

```text
/business/<business-slug>/
/business/<business-slug>/salon/
/business/<business-slug>/salon/customers/
/business/<business-slug>/salon/services/
/business/<business-slug>/salon/appointments/
/business/<business-slug>/salon/pos/
/business/<business-slug>/salon/sales/
```

SalonNEXT records such as customers, services, appointments, and sales are written to the SalonNEXT business database, not the central platform database.

## 8. Test PharmacyB and GraceryShopA

Create separate businesses and select their application during setup:

### PharmacyB

The business database receives:

- Medicine tables.
- Prescription tables.

### GraceryShopA

The business database receives:

- Product tables.
- Sale tables.

Each business gets a different database even when both businesses use the same application type.

## 9. Inspect database isolation

List PostgreSQL databases:

```bash
psql -h 127.0.0.1 -U bizflow -d bizflow_core -c '\l'
```

You should see:

```text
bizflow_core
bizflow_business_<business-a-uuid>
bizflow_business_<business-b-uuid>
```

Inspect tables in one business database:

```bash
psql -h 127.0.0.1 \
  -U bizflow \
  -d bizflow_business_<business-uuid> \
  -c '\dt'
```

The central database should contain platform tables. Business-specific tables should exist only in the relevant business database.

## 10. Retry failed provisioning

If provisioning fails:

1. Read the provisioning error in the platform business list or Django admin.
2. Fix the PostgreSQL permission, connectivity, or migration problem.
3. Run **Provision** again.

Provisioning uses an idempotency key and records completed steps. It can safely retry a partially completed business after the underlying problem is fixed.

If a database was created but migration failed, inspect the database before deleting it. A production cleanup process should be approved and logged.

## 11. SQLite isolated mode details

SQLite isolated mode is useful for:

- Authentication testing.
- Platform dashboard testing.
- Business membership testing.
- Demo dashboard metrics.
- Automated tests.
- Small single-server deployments.

Provisioning creates a file named `bizflow_business_<business_uuid>.sqlite3` in
`BIZFLOW_BUSINESS_DATABASE_DIR`, applies only the selected business application's
migrations, and marks the database `Ready` only after migration succeeds. Do not
share the directory between application instances without a shared-storage and
backup strategy.

## 12. Operational checklist

Before onboarding a real business:

- [ ] The selected database backend is configured.
- [ ] `BIZFLOW_BUSINESS_DATABASE_DIR` is writable when using SQLite.
- [ ] PostgreSQL is reachable when using PostgreSQL.
- [ ] Platform migrations are applied.
- [ ] The provisioning role has `CREATEDB`.
- [ ] Database passwords are stored outside source control.
- [ ] A unique business slug is selected.
- [ ] The correct business application is selected.
- [ ] Provisioning completes successfully.
- [ ] The business database status is `Ready`.
- [ ] The business status is `Active`.
- [ ] Owner login redirects correctly.
- [ ] Unauthorized business URL access returns `403`.
- [ ] Business-specific data appears only in the correct database.
- [ ] Backups and monitoring are configured.
